# PEP Camoufox: запуск на сервере

Из корня Git-репозитория. Excel берётся из `docs/DECLARACIONES_PEP.xlsx`,
вторая вкладка, колонка `ENLACE_CONSULTA_LEY_2013`. Он монтируется только для чтения.
Docker Compose v2 собирает браузер и модель в образ; ключи передаются при запуске.

## Настройки

При первом запуске скопируйте `.env.camoufox.example` в `.env.camoufox`.
В существующем файле обновите нужные строки, сохранив Telegram и другие ключи.
Для Webshare:

```dotenv
PEP_PROXY_PROVIDER=webshare
WEBSHARE_API_TOKEN=ваш_API_ключ
PEP_WORKERS=20
PEP_TABS=3
PEP_LIMIT=100
PEP_OFFSET=0
PEP_TIMEOUT=60
PEP_MAX_MINUTES=120
PEP_LOG_INTERVAL=30
PEP_MEMORY_LIMIT=24g
PEP_CPUS=8
PEP_SHM_SIZE=4gb
PEP_PIDS_LIMIT=8192
```

Ключ из основного `.env` нужно также указать в `.env.camoufox`: Compose передаёт
только перечисленные переменные. Webshare API вызывается один раз на старте
(с пагинацией), режим `direct`. Выбираются 20 валидных прокси с разными адресами;
один прокси закрепляется за браузером и его тремя вкладками. Если адресов меньше,
запуск завершается с сообщением о доступном количестве, без прямого fallback.
Сырые ответы API и proxy credentials на диск не сохраняются.

Для Bright Data замените настройки провайдера:

```dotenv
PEP_PROXY_PROVIDER=brightdata
BRIGHTDATA_PROXY_SERVER=http://brd.superproxy.io:44445
BRIGHTDATA_PROXY_USERNAME=базовый_логин_зоны
BRIGHTDATA_PROXY_PASSWORD=пароль
```

Программа добавляет отдельную sticky-сессию на браузер. Разные сессии Bright Data
могут дать одинаковые выходные IP. Перед обработкой каждый браузер проверяет
фактический IP через `https://api.ipify.org`; число разных IP отображается в отчётах.
`PEP_PROXY_PROVIDER=auto` выбирает Webshare при наличии его ключа, иначе Bright Data
при наличии credentials, иначе прямое соединение. Для прямого соединения разрешён
один браузер: `PEP_PROXY_PROVIDER=direct`, `PEP_WORKERS=1`.

TLS-проверка включена. Проверенный Sectigo intermediate для PEP импортируется
в отдельный профиль браузера. Закреплённый CA Bright Data импортируется только
для Bright Data, Webshare использует обычные доверенные CA.

## Сборка и запуск

```bash
docker compose --env-file .env.camoufox -f compose.camoufox.yml build
docker compose --env-file .env.camoufox -f compose.camoufox.yml up -d --force-recreate
docker compose --env-file .env.camoufox -f compose.camoufox.yml logs -f pep-camoufox
```

`20 × 3` означает 20 браузерных процессов с отдельными профилями и максимум
60 одновременно обрабатываемых ссылок. Если ссылок меньше 20, число браузеров
сокращается до числа ссылок. Пустые вкладки закрываются. Нативная инициализация
браузеров идёт последовательно из-за ранее наблюдавшегося сбоя fingerprint-библиотеки;
после запуска браузеры и вкладки работают параллельно. Каждая вкладка обрабатывает
декларации своей ссылки последовательно с прежними паузами 3 секунды.

Ссылки выбираются из общей очереди без повторов. Свободная вкладка сразу берёт
следующую, поэтому быстрые браузеры не ждут, пока медленный закончит свой набор.
При явном отказе reCAPTCHA прекращается выдача новых задач всем вкладкам
затронутого браузера. Уже выполняемые действия завершаются до ближайшей проверки
остановки. Остальные браузеры продолжают общую очередь. Сессии и прокси при отказе
не меняются, частичные декларации автоматически не повторяются.

Лимиты RAM/CPU/SHM/PID задаются переменными выше; это лимиты контейнера,
а не измеренная потребность 60 вкладок. Настройте их по ресурсам сервера.
Для наблюдения за фактическим потреблением:

```bash
docker stats --no-stream
```

## Параметры

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `PEP_INPUT` | `./docs/DECLARACIONES_PEP.xlsx` | Excel на сервере |
| `PEP_LIMIT` | `100` | Уникальные ссылки; `0` — все |
| `PEP_OFFSET` | `0` | Пропустить столько уникальных ссылок |
| `PEP_WORKERS` | `20` | Браузеры, 1–100 |
| `PEP_TABS` | `3` | Рабочие вкладки на браузер, 1–10 |
| `PEP_TAB_RESTARTS` | `3` | Замен упавшей вкладки на рабочее место за запуск, 0–100 |
| `PEP_TIMEOUT` | `60` | Таймаут отдельного действия, 5–120 секунд |
| `PEP_MAX_MINUTES` | `120` | Лимит времени браузера, включая ожидание его запуска |
| `PEP_LOG_INTERVAL` | `30` | Heartbeat, 5–300 секунд |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | пусто | Оба значения для Telegram |

Каждый запуск создаёт новый `run-<UTC>`. Очередь не возобновляется автоматически
после перезапуска; для следующей сотни задайте `PEP_OFFSET=100`.

## Отчёты и файлы

Общее сообщение в Telegram и `progress.jsonl` приходит каждые 10 завершённых
ссылок и один раз в конце. Содержит полные/пустые/частичные/ошибочные ссылки,
активные ссылки и остаток очереди, скачанные/нескачанные декларации, PDF,
время, скорость, число браузеров, вкладок и разных proxy IP.
Отсутствие полностью ошибочных ссылок не означает отсутствие недокачанных деклараций.

В volume `pep-camoufox-data`, каталог `/app/data/run-<UTC>/`:

- `report.json` — общий снимок, браузеры и вкладки, счётчики и причины остановки;
- `sample.json` — выбранные ссылки;
- `incomplete-documents.json` — итоговый список недокачанных деклараций с HTTP-кодами и причинами;
- `progress.jsonl` — статистика на границах уведомлений;
- `run.log` — постоянный общий JSON Lines лог;
- `worker-N/report.json`, `worker-N/profile/` — отчёт и отдельный профиль браузера;
- `worker-N/tab-M/report.json`, `run.log`, `pdf/`, `archives/`, `manifests/` — результаты вкладки.

Пути PDF/ZIP в общем отчёте включают браузер и вкладку. ZIP, PDF и SHA-256
проверяются перед отметкой успеха. У вкладок раздельные каталоги, поэтому
совпавшие ID деклараций в разных вкладках не перезаписывают файлы друг друга.

Heartbeat работает каждые `PEP_LOG_INTERVAL` секунд, даже когда ни одна ссылка
ещё не завершена: текущие этапы и их длительность для вкладок, общая очередь,
счётчики и средняя/интервальная скорость. `document_finished` и `link_finished`
содержат отдельную длительность, HTTP-код и ошибку. Логи ротируются:
10 МиБ и 3 резервные копии на файл; stdout Docker — 10 МБ × 3 файла.
Credentials, токены, cookies и тела POST не выводятся в логи.

Скопировать результаты:

```bash
mkdir -p pep-results
docker compose --env-file .env.camoufox -f compose.camoufox.yml cp pep-camoufox:/app/data/. ./pep-results/
```

Остановить с сохранением отчётов:

```bash
docker compose --env-file .env.camoufox -f compose.camoufox.yml stop
```

Проверить Excel без браузеров и Telegram:

```bash
docker compose --env-file .env.camoufox -f compose.camoufox.yml run --rm pep-camoufox /input/DECLARACIONES_PEP.xlsx --limit 10 --preview
```

При недокачанных или необработанных ссылках программа возвращает exit code 1;
автоматический рестарт отключён. Ошибка уведомления не удаляет результаты.
Сценарий 20 браузеров × 3 вкладки проверяется офлайн на распределение задач,
изоляцию прокси и файлов, общий прогресс и остановку соседних вкладок.
Рабочую скорость этого масштаба нужно измерить на сервере.

## Диагностика падений вкладок

Перед выдачей ссылок ожидаются результаты запуска всех запрошенных браузеров:
каждый должен либо пройти проверку прокси, либо завершить запуск с ошибкой.
При таймауте проверки IP выполняется ещё одна попытка с тем же браузером и прокси;
каждая попытка ограничена `PEP_TIMEOUT`. Событие `proxy_preflight_timeout` содержит
номер попытки и признак повтора, а `proxy_preflight_attempts` в отчёте — их число.
Если проверка Webshare не прошла, приложение закрывает браузер и запускает новый
со следующим свободным адресом из полученного списка. Один адрес назначается только
одному браузеру; допускается до трёх замен на браузер. При исчерпании адресов или
лимита замен браузер исключается из работы, остальные обрабатывают очередь.
Событие `proxy_replaced` и поля `proxy_replacements`, `proxy_failures` сохраняют
причину и число попыток без учётных данных. Bright Data не выбирает адреса из
списка Webshare. Замена выполняется до обработки ссылок; отказ сайта или CAPTCHA
во время обработки не вызывает смену прокси.
Событие `queue_released` показывает число готовых и не запустившихся браузеров.
Это позволяет поздно открывшимся браузерам участвовать в небольшой тестовой очереди.

При `TargetClosedError`, событии `crash` или ошибке `Target crashed` вкладка
прекращает брать новые ссылки. Её текущая ссылка сохраняет ошибку; оставшаяся
очередь остаётся доступна другим вкладкам. Если браузерный контекст ещё открыт,
есть задачи в очереди и не исчерпан `PEP_TAB_RESTARTS`, через секунду открывается
новая вкладка в том же контексте, профиле и прокси. Она берёт следующую ссылку;
ссылка, на которой произошло падение, автоматически не повторяется. Отказы сайта,
закрытие всего контекста и три подряд ошибки навигации не запускают замену.
После трёх подряд ошибок
навигации вкладка также останавливается с `consecutive_navigation_errors`.
Обычная ошибка документа оставляет текущую ссылку частичной, но не останавливает
соседние вкладки. Явный отказ сайта по-прежнему останавливает браузерную сессию.

`page_lifecycle` фиксирует закрытие/падение страницы, время, текущую задачу и
признак ожидаемого закрытия. `browser_context_closed` фиксирует закрытие контекста.
При таймауте ошибка снятия скриншота или чтения страницы не скрывает исходную
ошибку скачивания: сохраняются `error` и при необходимости `diagnostic_error`.

В `report.json` и heartbeat добавлено поле `resources`: доступные cgroup v2
счётчики `memory.current`, `memory.max`, `memory.peak`, `memory.events`,
`pids.current`, `pids.max`, а также общий и свободный объём `/dev/shm` в байтах.
`memory_events_since_start` показывает прирост событий за этот запуск, включая
`oom` и `oom_kill`, если они доступны. Отсутствующие счётчики не считаются ошибкой.
Сами сообщения `TargetClosedError` и `Target crashed` не устанавливают причину
падения: для проверки нехватки ресурсов нужны эти счётчики и системные логи сервера.

Попытки замены отмечаются `tab_restarting`, исчерпание лимита — `tab_restart_limit`.
Общее количество попыток (`tab_restarts`) выводится в статистике и Telegram.
Лимит задаётся отдельно для каждого рабочего места вкладки и сбрасывается
при новом запуске. `PEP_TAB_RESTARTS=0` отключает замену; при повторяющихся
падениях вкладка остановится после указанного числа замен.
Начальные результаты лежат в `worker-N/tab-M/`, результаты замен — в
`worker-N/tab-M/restart-K/`. `tab-M/summary.json` содержит объединённый отчёт
по всем поколениям вкладки, включая историю восстановления и исходные ошибки.
В общем `report.json` все поколения учитываются вместе, пути файлов включают
`restart-K/`, прежние результаты не перезаписываются.

## JSON с исходными данными политиков и PDF

`politicians.json` в корне `run-<UTC>/` обновляется вместе с общим отчётом
на границах прогресса, heartbeat и при завершении. Одна запись соответствует
уникальной ссылке политика:

```json
[
  {
    "excel_records": [
      {"excel_row": 2, "data": {"NAME": "Example", "OTHER_EXCEL_COLUMN": null}}
    ],
    "consultation_url": "https://www.funcionpublica.gov.co/fdci/consultaCiudadana/index?...",
    "status": "completed",
    "declarations": [
      {
        "id": "123",
        "publication_date": "2024-01-01",
        "publication_type": "...",
        "declaration_number": "...",
        "declaration_status": "...",
        "download_status": "downloaded",
        "pdfs": [
          {"path": "worker-1/tab-1/pdf/123.pdf", "sha256": "...", "size_bytes": 12345}
        ],
        "error": null
      }
    ],
    "error": null
  }
]
```

В `excel_records[].data` сохраняются все столбцы исходного Excel под их исходными
названиями, включая пустые значения и все дублирующиеся строки этой ссылки.
Даты Excel сериализуются в ISO. Исходная строка не заменяется данными сайта.
`declarations` содержит все найденные записи со всех пройденных страниц, включая
ошибочные и не скачанные. У таких деклараций нет фиктивных путей PDF.
Один ZIP может дать несколько PDF — все входят в `pdfs`.
`publication_date` — дата публикации на сайте, не автоматически определённый
год отчётности или период пребывания в должности. Полнота скачивания видна по статусам.

`pdfs[].path` задаётся относительно папки запуска. Копируйте всю папку запуска
вместе с JSON, сохраняя подкаталоги; тогда пути продолжат работать. Впоследствии
можно заменить эти значения на `s3://bucket/key`. Загрузка в S3 не выполняется.

Для уже существующего отчёта можно создать такой JSON без повторного скачивания:

```bash
docker compose --env-file .env.camoufox -f compose.camoufox.yml run --rm --no-deps \
  --entrypoint python pep-camoufox -m scripts.pep_camoufox_export \
  /app/data/run-20261104T194412033002Z/report.json /input/DECLARACIONES_PEP.xlsx
```

Предварительно пересоберите образ с новой версией кода. JSON появится рядом
с выбранным `report.json`. Политики связываются с Excel по нормализованной ссылке;
если для кого-либо не нашлось строки, экспорт завершается ошибкой.

## Уведомления по времени

В `.env.camoufox` задайте `PEP_TELEGRAM_INTERVAL_MINUTES=30`, чтобы получать
прогресс раз в полчаса вместо каждых 10 ссылок. Значение `0` сохраняет режим
каждых 10 ссылок. Итоговое уведомление отправляется при завершении независимо
от выбранного интервала; запуск короче 30 минут выдаст только итог.
Проверка интервала работает также в heartbeat, поэтому уведомления приходят
и при отсутствии новых завершённых ссылок. Точность интервала зависит от
`PEP_LOG_INTERVAL` (по умолчанию 30 секунд) и времени отправки Telegram.
Постоянные логи и сохранение отчётов продолжают обновляться с прежней частотой.
После обновления кода пересоберите образ и пересоздайте контейнер.

## Дозагрузка в исходную папку запуска

`--retry-report` выбирает неполные ссылки и ссылки с повреждёнными PDF.
`--limit` и `--offset` при дозагрузке не применяются. Корнем результата остаётся
папка указанного отчёта; готовые PDF сохраняют прежние пути и не копируются.
Новые PDF и технические отчёты попытки сохраняются внутри неё в `retries/run-<UTC>/`.

После обновления и сборки образа:

```bash
docker compose --env-file .env.camoufox -f compose.camoufox.yml run -d \
  --name pep-camoufox-retry --no-deps pep-camoufox \
  /input/DECLARACIONES_PEP.xlsx \
  --retry-report /app/data/run-20261105T101627365188Z/report.json \
  --workers 25 --tabs 3 --timeout 120 --max-minutes 120

docker logs -f pep-camoufox-retry
```

В исходной папке атомарно обновляются `report.json`, `politicians.json` и
`incomplete-documents.json`. Они объединяют всех политиков исходной выборки,
а не только ссылки текущей попытки. Обновление выполняется при прогрессе,
heartbeat и завершении. Резервные копии предыдущих отчётов лежат в
`retries/before-run-<UTC>.json`; технический отчёт отдельного прохода — в
`retries/run-<UTC>/report.json`. Вложенные относительные пути в общем JSON
нормализуются относительно исходной папки. Для переноса достаточно скопировать
её целиком со всеми подкаталогами.

Проверенные PDF повторно не скачиваются. Исходные документы сохраняются и при
ошибке повторного открытия страницы. Перед запуском проверяются локальные
manifest/SHA-256, поэтому повреждённый документ может попасть в дозагрузку.
Сохранение отчёта при прерывании позволяет снова использовать тот же
`--retry-report .../report.json`. Каждая команда выполняет один проход.

Блокировка `.retry.lock` защищает папку от одновременных дозагрузок и снимается
при завершении процесса. Если контейнер `pep-camoufox-retry` остался от завершённой
попытки, перед следующей удалите его командой `docker rm pep-camoufox-retry`.
Volume с результатами сохраняется. Основное скачивание и дозагрузку лучше
запускать по очереди, чтобы не удваивать нагрузку сервера.

## Старые ссылки деклараций

Legacy-ссылки `/ley-transparencia-web/declaracionServlet` могут открывать новую
вкладку (`target="_blank"`). Загрузчик наблюдает её скачивание и HTTP-ответы
точного URL документа, включая ответы до появления доступного frame. Поэтому
404/407/другие ошибки больше не должны маскироваться таймаутом ожидания загрузки
в исходной вкладке. На действительной ссылке из тестового набора после успешной
проверки Webshare подтверждён HTTP 404; PDF по этому адресу сервер не вернул.
Это не устанавливает доступность остальных legacy-документов.

## Недоступные legacy PDF и уведомления

Подтверждённый HTTP 404 от старого `declaracionServlet` сохраняется как
`unavailable_http_404`, вместе с датой, типом публикации и исходной ссылкой.
`OTRO` сам по себе не исключается. Если остальные документы ссылки скачаны,
статус ссылки — `completed_with_unavailable`. Такие PDF не считаются скачанными,
но исключаются из обычных повторов и из счётчика нерешённых ошибок.
Они перечислены отдельно в `unavailable-documents.json` и остаются в `politicians.json`.

Повторный запуск `--retry-report` по старому отчёту классифицирует подтверждённые
legacy `http_404`; если других задач нет, обновляет JSON с резервной копией
и завершает работу без браузеров. Таймаут или 404 современного endpoint
автоматически недоступным legacy-документом не считается.

Telegram получает стартовое сообщение один раз после готовности браузеров
и проверок прокси, перед выдачей задач. В сообщении показываются готовые
браузеры и разные proxy IP. Далее идут сообщения по настроенному интервалу
и итог. Разделы сообщений: ссылки, декларации, недоступные legacy PDF,
таймауты/HTTP 302, браузеры, время и скорость новых скачиваний.
Наличие `completed_with_unavailable` не вызывает exit code 1 само по себе;
неразрешённые частичные ссылки и реальные ошибки по-прежнему дают exit code 1.

Для первого тестового батча 5000 ссылок обновите `.env.camoufox`:

```dotenv
PEP_LIMIT=5000
PEP_OFFSET=0
PEP_WORKERS=25
PEP_TABS=3
PEP_MEMORY_LIMIT=40g
PEP_CPUS=12
PEP_SHM_SIZE=4gb
PEP_PIDS_LIMIT=8192
PEP_MAX_MINUTES=360
PEP_TELEGRAM_INTERVAL_MINUTES=30
```

Это новый прогон первых 5000 уникальных ссылок, включая ранее проверенные первые
1000. Запускайте его после завершения дозагрузки. Стандартная сборка и
`up -d --force-recreate` используют эти настройки; старые папки результатов
остаются в volume. 360 минут — предел времени, а не обещание длительности.
# Автоматическое продолжение

Обычный запуск автоматически читает `/app/data/run-*/report.json` и проверяет
сохранённые PDF по контрольным суммам. Готовые ссылки, включая пустые результаты
и обработанные ссылки с legacy 404, пропускаются. Для частичных ссылок
переиспользуются проверенные документы; остальные скачиваются заново.

Каждый запуск создаёт новую самостоятельную папку `run-...`: общий
`politicians.json` содержит выбранные записи Excel и пути к PDF внутри этой папки.
Старые PDF добавляются жёсткими ссылками (при невозможности — копированием),
поэтому удаление старой папки не ломает новый набор. Старые отчёты не изменяются.
Сканируются только корневые отчёты запусков, с учётом внесённых в них retry.
Подтверждённые legacy 404 повторно не запрашиваются. Для обновления уже
завершённых записей с портала используйте явный `--fresh`.

Для полного набора после завершения текущего батча установите в `.env.camoufox`:

```dotenv
PEP_LIMIT=0
PEP_OFFSET=0
PEP_MAX_MINUTES=2880
PEP_WORKERS=25
PEP_TABS=3
PEP_TELEGRAM_INTERVAL_MINUTES=30
```

`PEP_LIMIT=0` выбирает все уникальные ссылки Excel. Затем пересоберите образ и
пересоздайте контейнер обычными командами `build` и `up -d --force-recreate`.
Не удаляйте volume. Поиск старых результатов выполняется в том же volume;
файлы вне него автоматически не импортируются. В Telegram отдельно показаны
готовые ссылки прошлых запусков и новые/переиспользованные декларации.
Одновременные обычные запуски в одном каталоге результатов блокируются.

## Ротация браузеров на длительном прогоне

```dotenv
PEP_BROWSER_MAX_MINUTES=20
PEP_BROWSER_MAX_LINKS=40
```

Порог останавливает выдачу новых ссылок конкретному браузеру. Его текущие
вкладки завершают взятые ссылки, затем весь браузер закрывается и запускается
заново с тем же профилем и прокси. Очередь и результаты сохраняются. Файлы новых
поколений лежат в `tab-N/restart-K`, общий JSON содержит корректные пути ко всем
поколениям. Порог времени отсчитывается после готовности браузера; начальные
интервалы немного различаются между браузерами, чтобы разнести ротации.
Одна длинная ссылка может продлить фактическую жизнь браузера сверх порога.

Штатные ротации показаны отдельно как `browser_restarts` в отчёте и Telegram;
они не увеличивают счётчик аварийных замен вкладок. В событиях есть
`browser_draining` и `browser_restarting`, причина, поколение и ресурсы контейнера.
Лимит общего времени запуска действует на все поколения вместе.
Временная загрузка Playwright удаляется после копирования, вспомогательное окно
скачивания закрывается, промежуточный `.bin` удаляется после проверки PDF.

Для сервера 61 GiB / 16 CPU после достижения лимита 40 GiB начните с
20 браузеров × 3 вкладки и оставьте `PEP_MEMORY_LIMIT=40g`.
Настоящее поведение памяти на многочасовом серверном прогоне нужно проверить
по `docker stats` и `memory.events`; короткая проверка ротации не заменяет её.

Общий `report.json` и экспорт всего Excel записываются не чаще раза в 15 секунд
при обновлениях работников, дополнительно на heartbeat и обязательно при
завершении. Запись выполняется в фоновом потоке, чтобы сброс на диск не задерживал
браузерные события. Контрольные точки отдельных вкладок сохраняются отдельно;
общий отчёт может отставать на один интервал.
Для таймаутов поле `error.stage` различает `waiting_download_event`,
`saving_file` и `validating_file`. Один HTTP 200 не подтверждает получение PDF.
# Текущее сохранение состояния: SQLite

В обычных запусках основной файл состояния — `run-<UTC>/state.sqlite3`.
Полные записи Excel, документы, ошибки и пути PDF хранятся в SQLite, а не
перезаписываются в общий JSON после каждой ссылки. Таблица `links` содержит
`url`, `n`, `status`, `payload` (полная запись JSON), `updated_at`.
Таблица `documents` содержит `url`, `id`, `status`, `local_path`, `payload`
(все поля декларации). Есть индексы статусов и уникальные ключи ссылок/документов.

До 500 изменённых ссылок вместе с декларациями фиксируются одной транзакцией.
Остаток фиксируется раз в минуту и при штатном завершении/остановке. При
принудительном SIGKILL можно потерять ещё не зафиксированный остаток; готовые PDF
останутся на диске. Используются WAL и один сериализованный писатель.
Глобальные и повкладочные JSON-отчёты в обычном SQL-режиме не перезаписываются.
Логи и Telegram остаются. Небольшие манифесты PDF сохраняются для проверки файлов.

Проверить статусы последнего запуска:

```bash
docker compose --env-file .env.camoufox -f compose.camoufox.yml exec -T pep-camoufox \
  python -m scripts.pep_camoufox_db /app/data --stats
```

Сформировать `report.json`, `politicians.json` и `unavailable-documents.json`
отдельно из последней БД:

```bash
docker compose --env-file .env.camoufox -f compose.camoufox.yml exec -T pep-camoufox \
  python -m scripts.pep_camoufox_db /app/data
```

Экспорт использует согласованный снимок SQLite и может выполняться во время
скачивания; после него сборщик продолжает менять только БД. Если контейнер
остановлен, ту же команду можно выполнить через отдельный контейнер:

```bash
docker compose --env-file .env.camoufox -f compose.camoufox.yml run --rm --no-deps \
  --entrypoint python pep-camoufox -m scripts.pep_camoufox_db /app/data
```

Обычный запуск автоматически продолжает по БД прошлых запусков и по старым
`report.json`. При наличии обоих файлов в папке БД имеет приоритет. Для старого
явного режима `--retry-report` сохранена совместимость с JSON; для новых запусков
рекомендуется обычное автопродолжение. Команды чтения `report.json` в разделах
выше относятся к старым запускам либо к явно сформированному экспорту.

## Таймауты навигации

Навигация ждёт HTTP commit, завершение разбора HTML и таблицу результатов,
а не DOMContentLoaded (который может задерживаться отложенными скриптами).
Проверяются маршрут и идентификатор запрошенного человека: прежняя таблица или
общий текст справки не считаются результатом. При ошибке сохраняются
`navigation_stage`, `landing_http_status`, по возможности `navigation_readiness`.

После трёх последовательных таймаутов навигации допускается до трёх восстановлений
браузера с тем же прокси и паузами 30/60/120 секунд. Событие `navigation_cooldown`
показывает номер попытки и паузу. Это ограниченное восстановление не применяется
к ошибкам HTTP или явным отказам сайта. Неуспешные ссылки остаются в БД для
следующего автопродолжения. Если таблица не загружается и после пауз, работник
останавливается; бесконечные повторные запросы не выполняются.

## Общая пауза при массовых таймаутах

```dotenv
PEP_SITE_PAUSE_MINUTES=20
```

Если за последние 180 секунд таймауты навигации произошли минимум у половины
браузеров (округление вверх, минимум два при наличии нескольких браузеров),
приостанавливается выдача новых ссылок всей очереди. Для 25 браузеров порог —
13 разных браузеров. Повторные ошибки вкладок одного браузера не увеличивают
число затронутых браузеров; таймауты скачивания отдельных документов и HTTP
ошибки не запускают эту паузу.

Текущие ссылки завершаются, затем браузеры закрываются на время ожидания.
Через 20 минут только один браузер проверяет таблицу результатов проблемной
ссылки, с тем же прокси. При успехе очередь возобновляется, при неудаче общая
пауза повторяется на 20 минут. Эти паузы действуют в рамках общего лимита времени
`PEP_MAX_MINUTES`; оператор может штатно остановить процесс в любой момент.

О начале, продлении паузы и возобновлении приходит немедленное Telegram-сообщение,
независимо от обычного интервала в 30 минут. Поле `site_pause` сохраняется в БД,
heartbeat и progress.jsonl; события `site_paused`, `site_probe_failed` и
`site_resumed` записываются в run.log. Перед уведомлением остаток записей БД
принудительно фиксируется. Пауза координируется в рамках текущего процесса;
новый запуск заново оценивает доступность сайта.

## Повторяющиеся ID деклараций

Одинаковый ID на одной странице обрабатывается один раз. Перед записью SQLite
декларации дополнительно объединяются по строковому ID: скачанный документ
имеет приоритет перед pending/running/error. Исходные варианты полей сохраняются
в `source_rows` в payload и отчётном JSON. Таблица `documents` использует UPSERT;
ограничение уникальности `(url,id)` остаётся включённым.

Для продолжения после старого `UNIQUE constraint failed: documents.url,
documents.id` достаточно обновить образ и запустить обычное автопродолжение.
Схема БД не меняется. Зафиксированные транзакции сохраняются; незаписанный
остаток и записи running из остановленного запуска выбираются повторно.
При ошибке финального сохранения итоговое уведомление теперь всё равно
отправляется с причиной `state_write_failed`, а процесс завершается с ошибкой.
