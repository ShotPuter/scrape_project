# RES на сервере: самостоятельный сбор с нуля

Новая команда `pipeline` сама создаёт БД, собирает компании из публичных sitemap
DeQuienes, проверяет их в RES и скачивает все найденные PDF. Перенос старых
БД, результатов или профилей не требуется. Аккаунт Google для этого пути не нужен.

## Подготовка

Нужны Docker с Compose v2 и настройки Webshare/Telegram. На сервере возьмите
актуальную ветку проекта. Пустой каталог данных создайте до старта Compose:

```bash
mkdir -p data
sudo chown 1000:1000 data
```

Если на сервере уже есть другой сбор, укажите новый пустой каталог в
`RES_DATA_DIR`. Существующие результаты удалять не нужно.

Образ запускается пользователем UID/GID 1000. Каталог `data` должен существовать
и быть ему доступен на запись. При необходимости на сервере создайте отдельный
каталог, назначьте владельца `1000:1000` и укажите его через `RES_DATA_DIR`.
По умолчанию подключается `./data` в `/app/data`; файл
`dequienes-companies-2025/companies.sqlite3` создаётся автоматически.

```bash
cp .env.res.example .env.res
# Впишите WEBSHARE_API_TOKEN, TELEGRAM_BOT_TOKEN и TELEGRAM_CHAT_ID в .env.res.
chmod 600 .env.res
docker compose --env-file .env.res -f compose.res.yml build res

# Проверить Telegram до сбора (БД и браузер не нужны).
docker compose --env-file .env.res -f compose.res.yml run --rm res telegram-test
```

Секреты читаются из окружения контейнера. `.env.res`, локальные данные,
профили и токены исключены из контекста сборки. Браузер и модель fingerprint
загружаются при сборке, при обычном старте повторная загрузка не нужна.
Встроенный Xvfb позволяет работать без монитора; `--headed` на сервере не нужен.

На чистом сервере создайте `.env.res` из примера и задайте свои ключи.
Локальный файл с ключами не входит в Git или образ.

Текущий образ `chile-res:local` собран с уже загруженными публичными файлами
Camoufox и проверенной моделью. Официальный архив браузера около 1,3 GB,
поэтому повторная загрузка может быть долгой. Если эти файлы уже есть локально:

```bash
docker build -f Dockerfile.res -t chile-res:local \
  --build-arg CAMOUFOX_ASSETS=cache \
  --build-context browser-assets=./data/camoufox-cache/camoufox/browsers \
  --build-context model-assets=./.camoufox-deps/fpgen/data .
```

В этом режиме копируются только файлы браузера и модели, без пользовательских
профилей и настроек. Проверка модели/пути бинарника выполняется без сети.
Обычный `compose build` на чистом сервере использует официальный download.
Готовый образ также можно перенести через `docker save` / `docker load`.

## Запуск и остановка

Параметры по умолчанию: январь 2025 года, 100 уникальных компаний.
`RES_YEAR` и `RES_MONTH` задают источник; `RES_LIMIT` — число компаний.
DeQuienes сначала использует один Camoufox для сессии и четыре HTTP-обработчика
через тот же Webshare-прокси. После достижения цели открывается пул RES
`RES_BROWSERS` × `RES_TABS_PER_BROWSER` (по умолчанию 5 × 2).
После поиска автоматически скачиваются все CVE выбранных компаний; лимит
PDF отдельно не ограничен. Поиск и скачивание используют одни и те же
сохранённые прокси/профили последовательно.

Повторные публикации компании не считаются новыми компаниями. Из-за уже
выполняющихся запросов в БД может оказаться на несколько компаний больше;
для RES фиксируется ровно `RES_LIMIT` ID. Если выбранный месяц не дал нужного
числа компаний или сбор остановился, RES не стартует с неполной выборкой.
Состояние и выборка сохранены в `pipelines/<run_id>.json`, отчёт начального
этапа — `public_collection/<run_id>-public.json`. Источник и лимит при повторе
того же ID менять нельзя; число браузеров можно.

```bash
# С нуля: сбор компаний, проверка 100 компаний в 5 × 2 вкладках, затем все PDF.
docker compose --env-file .env.res -f compose.res.yml up -d res
docker compose --env-file .env.res -f compose.res.yml logs -f res

# Остановка с сохранением: Compose отправляет SIGINT, даёт до минуты на выход.
docker compose --env-file .env.res -f compose.res.yml stop res

# После первого создания БД — посмотреть общую статистику.
docker compose --env-file .env.res -f compose.res.yml run --rm res status

# Продолжение своего запуска с явным повтором CAPTCHA/ошибок:
docker compose --env-file .env.res -f compose.res.yml run --rm res pipeline \
  --year 2025 --month 1 --limit 100 --run-id res-companies-100 \
  --browsers 5 --tabs-per-browser 2 --proxy-provider webshare \
  --rate-per-minute 6 --retry-errors
```

Можно запускать этапы отдельно: `collect` передаёт аргументы сборщику
публичного архива, `search` — поиску RES, `download` — скачиванию. Для
самостоятельного `collect` предел уникальных компаний задаёт `--company-target`,
а `--limit` по-прежнему означает число публикаций. В `pipeline --limit` всегда
число компаний. Пример отдельного первого этапа:

```bash
docker compose --env-file .env.res -f compose.res.yml run --rm res collect \
  --year 2025 --month 1 --company-target 100 --workers 4 \
  --transport hybrid --proxy-provider webshare \
  --output data/dequienes-companies-2025 --profile data/res-public-profile
```

`run --rm` в последней команде создаёт отдельный контейнер: сначала остановите
старый, чтобы не занимать одни и те же профили. Ctrl+C для foreground-команды
завершает обработку с сохранением. Для `up -d` используйте `stop res`.
Сеть, имена запусков и данные остаются прежними при повторном старте.
Уже завершённые компании пропускаются; общий бюджет — 100 разных компаний,
а не 100 на браузер. `RES_RATE_PER_MINUTE` общий для всей стадии.

## Все найденные PDF конкретного запуска

```bash
docker compose --env-file .env.res -f compose.res.yml run --rm res download \
  --from-search-run res-companies-100 --limit all --run-id res-companies-100-pdf \
  --browsers 5 --tabs-per-browser 2 --proxy-provider webshare \
  --rate-per-minute 6
```

`--limit all` не ограничивает число CVE, `--from-search-run` выбирает только
компании указанного запуска. Чужие CVE из общей очереди не подмешиваются.
Если поиск был прерван, скачиваются уже найденные документы. Повтор той же
команды после продолжения поиска подхватит новые CVE, сохранив завершённые PDF.
Для повторения ошибок скачивания дополнительно укажите `--retry-errors`.

## Telegram

Для поиска и скачивания используются те же `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID`, что и в прежнем сборщике. Локальный `.env.res` уже дополнен
ими из существующего `.env`, без вывода секретов. На сервере задайте эти
значения в новом `.env.res`; Compose передаёт их в окружение, не в образ.

Уведомления каждого этапа, включая начальный сбор компаний, приходят при
запуске, после подготовки всех настроенных браузеров,
каждые 5 минут и при завершении/остановке, включая CAPTCHA и Ctrl+C. Готовность
означает, что вкладки созданы и проверка прокси завершена. При ленивом запуске
меньшего числа браузеров сообщение «все готовы» не отправляется; фактическое
число подготовленных браузеров видно в статусе и итоге.

Статус содержит этап и ID запуска, обработанные/активные задания, успешные
результаты, отсутствие записей/CVE, неоднозначные совпадения, ошибки и CAPTCHA,
число найденных CVE или сохранённых PDF, браузеры/вкладки, проверенные прокси,
длительность и причину остановки.

```bash
# Отправить одно проверочное сообщение; очередь и браузеры не запускаются.
docker compose --env-file .env.res -f compose.res.yml run --rm res telegram-test
```

Интервал задаётся в `.env.res`: `RES_TELEGRAM_INTERVAL_MINUTES=5` или `10`.
Для отдельной команды можно передать `--telegram-interval-minutes 10`.
`--no-telegram` отключает отправку для данного запуска. `status`, `export`
и `--help` сообщений не отправляют. При отсутствии обеих учётных настроек
сбор работает без Telegram; неполная настройка отмечается в консоли.

Отправка выполняется в фоне с ограничением времени. Ошибки Telegram не
останавливают сбор и не меняют результаты очереди. При штатном выходе скрипт
ожидает отправку итогового сообщения до 35 секунд. После принудительного
SIGKILL уведомление не гарантируется; сохранённая БД остаётся источником
продолжения. Журнал доставки без токенов/паролей хранится в
`res_searches/<run_id>.telegram.jsonl` или `res_downloads/<run_id>.telegram.jsonl`;
счётчики отправок/ошибок и интервал находятся в поле `telegram` отчёта.

В подключённом каталоге сохраняются БД, PDF, manifest, профили и промежуточные
JSON/CSV (после каждого результата и каждые 15 секунд). Команды `status` и
`export` работают без браузеров/сети. Отчёты лежат в
`data/dequienes-companies-2025/res_searches/res-companies-100.json` и
`res_downloads/res-companies-100-pdf.json`, общая выгрузка файлов — `document_files.csv`.

## Как выбираются прокси

`--proxy-provider webshare` требует токен и не переключается на прямое соединение
при ошибке. `auto` использует Webshare, если токен задан в окружении или `.env`,
иначе direct; `direct` отключает прокси явно. В Docker задан webshare.

Из Webshare API берутся действительные HTTP-прокси. Для каждого браузера
случайно выбирается отдельный адрес; все его вкладки используют этот адрес.
Для пяти браузеров нужны минимум пять уникальных адресов. Перед запросами RES
проводится IP-проверка через сам браузер. В отчёте `proxy_routes` указаны
идентификатор маршрута, успешность проверки и наблюдаемый IP, без логина/пароля.

В каждом профиле `res-proxy.json` хранит только provider и хеш адреса.
После перезапуска адрес восстанавливается из свежего inventory, актуальные
пароли снова берутся у Webshare. Если адрес исчез, запуск останавливается
с объяснением. Для намеренного нового назначения остановите сбор и удалите
`res-proxy.json` соответствующего профиля; это явное действие оператора.
Автоматическая смена прокси после CAPTCHA или блокировки не выполняется.

На сервере сложная CAPTCHA по-прежнему требует оператора с графическим доступом.
При её появлении пул останавливает новые задания и сохраняет очередь;
наличие прокси не гарантирует завершение 100 проверок без CAPTCHA.

Проверка реализации: 157 тестов прошли; Webshare API действительно выдал
пять разных случайно выбранных адресов, без открытия браузеров. Образ собран
через режим cache. В контейнере с отключённой сетью проверены CLI, чтение
снимка БД, выбор только CVE указанного запуска, UID 1000, Xvfb, бинарник
Camoufox и контрольная сумма модели. Браузеры и сбор после остановки не
запускались; реальная работа браузеров через Webshare остаётся серверным тестом.
Одно проверочное Telegram-сообщение действительно доставлено из обновлённого
контейнера; готовность, периодический статус и прерывание проверены тестами
с подменой транспорта, без дополнительных живых сообщений.
Новый pipeline дополнительно проверен на пустом каталоге внутри контейнера
без сети: создание БД, выбор компаний, реальные очереди RES, сохранение
тестового PDF и повторный запуск без повторной обработки; ответы сайтов
в этой проверке подменялись. Старые данные не подключались.
