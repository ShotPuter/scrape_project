# RES: сбор компаний, CVE и PDF в Docker

По умолчанию Compose запускает `benchmark`: официальный открытый API RES →
список компаний/RUT → поиск действий/CVE → Verificar Certificados → PDF.
DeQuienes, Google-аккаунт, старые БД и браузерные профили не нужны. Источник
содержит компании, зарегистрированные по упрощённому режиму; это не полный
справочник всех чилийских компаний.

Camoufox получает настоящие CAPTCHA-токены; поиск и загрузка PDF идут через
HTTP по тому же Bright Data-прокси. Браузер работает на виртуальном дисплее,
монитор не требуется. Whisper base распознаёт аудио локально на CPU. Платный
CAPTCHA API не используется; трафик/сессии Bright Data оплачиваются по тарифу
провайдера. Не каждый CAPTCHA-вызов проходит: ошибки остаются в отчёте.

## Подготовка и запуск 100 компаний

На сервере нужны Docker Engine с Compose v2, Linux x86_64, свободное место для
образа/браузера/моделей и PDF. Начальные лимиты контейнера: 6 CPU, 12 ГБ памяти,
2 ГБ shared memory. Не назначайте больше ресурсов, чем есть на сервере.

```bash
cp .env.res.example .env.res
mkdir -p data
```

Заполните `.env.res` (не публикуйте файл):

```dotenv
BRIGHTDATA_PROXY_SERVER=http://brd.superproxy.io:44445
BRIGHTDATA_PROXY_USERNAME=YOUR_USERNAME
BRIGHTDATA_PROXY_PASSWORD=YOUR_PASSWORD
RES_PROXY_PROVIDER=brightdata
RES_YEAR=2025
RES_MONTH=1
RES_LIMIT=100
RES_RUN_ID=res-2025-01-100
RES_BROWSERS=2
RES_MAX_DOCUMENTS=0
RES_COMPANY_ATTEMPTS=2
RES_TOKENS_PER_PROXY=20
RES_RETRY_ERRORS=0
```

`RES_MAX_DOCUMENTS=0` скачивает **все CVE, найденные для выбранной компании**.
Значение `1` ограничивает тест одним PDF на компанию. Полнота результатов зависит
от ответа поиска RES; наличие компании в открытом наборе не гарантирует PDF.
Для проверки 150 компаний задайте `RES_LIMIT=150` и новый
`RES_RUN_ID=res-2025-01-150`.

```bash
docker compose --env-file .env.res -f compose.res.yml build res
# Подготовить только каталог результатов; образ работает от UID/GID 1000.
docker compose --env-file .env.res -f compose.res.yml run --rm --user 0 --entrypoint sh res \
  -c 'mkdir -p /app/data/res-benchmark && chown 1000:1000 /app/data/res-benchmark'
docker compose --env-file .env.res -f compose.res.yml up -d res
docker compose --env-file .env.res -f compose.res.yml logs -f --tail=100 res
```

Первичная сборка скачивает Python-зависимости, браузеры, модель отпечатков и
Whisper base. Эти публичные ресурсы находятся в образе; при старте Whisper
использует локальный кеш, а не скачивает модель. Секреты, локальные `.env`,
старые PDF и профили исключены из build context. Bright Data CA добавляется
только в частный профиль/HTTP-клиент, системная проверка TLS не отключается.

## Параллелизм и прокси

`RES_BROWSERS=2` — два независимых Python-процесса и браузера. У каждого одна
вкладка CAPTCHA, собственные HTTP-сессия, состояние и профиль. Это позволяет
обрабатывать компании параллельно, не смешивая одноразовые токены. Для пяти
браузеров задайте `RES_BROWSERS=5` **до первого запуска новой выборки**; оцените
память и CPU по фактическому использованию. Число браузеров после фиксации
выборки не меняется: для другого числа нужен новый `RES_RUN_ID`.

Новые Bright Data sticky-сессии создаются по мере необходимости. На старте
каждой проверяется совпадение IP браузера и HTTP. `RES_TOKENS_PER_PROXY` задаёт
бюджет токенов до смены сессии. `RES_PROXY_SESSIONS=0` рассчитывает конечный
бюджет на процесс: число компаний × число попыток + 5. Положительное значение
ограничивает этот бюджет явно. Прямого подключения к RES при ошибке прокси нет.

HTTP повторяет установление соединения один раз до отправки запроса. GET также
имеет один повтор при транспортной ошибке/502/503/504. Уже отправленный POST с
CAPTCHA-токеном повторно не проигрывается. Техническая ошибка компании может
попасть в очередь для новой попытки, максимум `RES_COMPANY_ATTEMPTS` за запуск.

Альтернатива: `RES_PROXY_PROVIDER=webshare` и `WEBSHARE_API_TOKEN`. Работа CAPTCHA
на Webshare менее предсказуема по прошлым пробам; это отдельный режим сравнения.
Классификация текущей Bright Data-зоны как residential/ISP/datacenter автоматически
не определяется.

## Где смотреть прогресс, PDF и скорость

При стандартном `RES_DATA_DIR=./data` результаты находятся в:

```text
data/res-benchmark/res-2025-01-100/
  selection.json             # неизменная выборка и ссылка на официальный ресурс
  companies.sqlite3          # company_id, company_name, rut
  progress.json              # обновляется каждые 15 секунд
  summary.json               # итог текущего запуска и состояние всей выборки
  results.csv                # компания, RUT, статус, CVE/PDF, попытки и секунды
  benchmark-<timestamp>.json  # история измерений каждого запуска/продолжения
  workers/w00/               # отдельное состояние первого процесса
    state.json               # найденные CVE и серверные ссылки codigo
    queue.sqlite3
    report-<timestamp>.json   # попытки, CAPTCHA, HTTP-время, прокси
    worker-<timestamp>.log
    pdf/<cve-hash>/           # PDF с SHA-256 в имени + manifest.json
```

Остальные процессы находятся в `workers/w01/` и т. д. В CSV пути PDF указаны
относительно каталога запуска. Все файлы сохраняются на хосте через bind mount.

```bash
cat data/res-benchmark/res-2025-01-100/progress.json
cat data/res-benchmark/res-2025-01-100/summary.json
# Подробные сообщения браузера/Whisper:
tail -f data/res-benchmark/res-2025-01-100/workers/w*/worker-*.log
```

Итоговый отчёт содержит:

- `elapsed_seconds` — полное время текущего запуска, включая получение списка,
  загрузку локальной модели и подготовку браузеров; сборка образа не включается;
- `seed_seconds` — получение/чтение списка компаний;
- `new_pdfs`, `new_pdf_bytes`, `new_pdfs_per_minute` — только новые файлы текущего
  запуска, без прибавления ранее скачанных PDF;
- `pdf_count`, `companies_with_pdf` — накопленный результат всей выборки;
- `company_attempts_per_minute`, среднее, p50 и p95 секунд на попытку компании;
- `http_metrics` — вызовы и суммарные секунды поиска, деталей, проверки CVE и
  загрузки; суммы по параллельным процессам могут превышать полное время;
- статусы ошибок, число принятых токенов и способ получения (`native`/`audio`).

Для сравнения скорости меняйте число браузеров в **новом run-id** при одинаковых
годе, месяце, лимите и `RES_MAX_DOCUMENTS`, используя отдельный каталог данных
или отдельную tracking-БД (см. ниже). Повторный запуск с готовыми файлами
измеряет продолжение, а не скорость нового полного сбора.

## Остановка и продолжение

```bash
docker compose --env-file .env.res -f compose.res.yml stop res
docker compose --env-file .env.res -f compose.res.yml up -d res
```

Сохраняйте тот же `RES_RUN_ID`, год, месяц, лимит и число браузеров. Выборка не
запрашивается заново, завершённые компании пропускаются до запуска браузеров,
каждый найденный CVE/`codigo` сохраняется сразу. Валидные PDF проверяются по
манифесту и SHA-256 и повторно не скачиваются. Частично обработанная компания
продолжается с сохранённого шага. Весь каталог `RES_DATA_DIR` должен оставаться
на месте; удаление контейнера его не очищает.

Сохранённые ошибки автоматически не повторяются при обычном перезапуске. Для
нового ограниченного прохода по ошибкам включите `RES_RETRY_ERRORS=1` в `.env.res`:

```bash
docker compose --env-file .env.res -f compose.res.yml up -d --force-recreate res
```

Готовые PDF при этом пропускаются. Для следующего обычного продолжения верните
`RES_RETRY_ERRORS=0`. Можно менять таймауты, число попыток, провайдера прокси и
лимит документов на компанию, сохраняя тот же run-id. Увеличение лимита документов
докачает недостающие PDF; год/месяц/размер выборки/число процессов неизменны.

Код выхода `0` означает отсутствие незавершённых/ошибочных компаний; `2` —
частичный результат (в том числе CAPTCHA), `1` — ошибка подготовки, `130` —
остановка. Подробности находятся в JSON и логах. `restart: "no"` предотвращает
бесконечные повторы платных прокси-сессий.

## Telegram

Необязательно задайте `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` и
`RES_TELEGRAM_INTERVAL_MINUTES=5` (или `10`). Сообщения: запуск, подтверждённая
готовность браузеров, периодический прогресс, итог и скорость. Ошибка Telegram
не останавливает сбор. Пустые настройки отключают отправку.

Периодическое сообщение содержит обработанные компании, число новых PDF,
PDF/мин, ошибки попыток, CAPTCHA и активные процессы. Ошибка подготовки также
отправляет сообщение с причиной и путём к диагностике.

Проверка доставки без запуска браузеров и сбора:

```bash
docker compose --env-file .env.res -f compose.res.yml run --rm res telegram-test
```

После изменения `.env.res` пересоздайте контейнер, чтобы он получил новые значения:

```bash
docker compose --env-file .env.res -f compose.res.yml up -d --force-recreate res
```

Старые команды `pipeline`, `collect`, `search`, `download` остаются отдельными
точками входа для прежних очередей; новый Compose использует `benchmark` и
собственное хранилище. Новый пайплайн не меняет старую БД DeQuienes.

## Общая SQLite-БД отслеживания

Новый пайплайн пишет данные в `data/res-benchmark/tracking.sqlite3` сразу после
каждого этапа. База общая для всех процессов и пакетов на одном сервере;
используются WAL, внешние ключи и ограниченное ожидание блокировки записи.

| Таблица | Что хранит |
| --- | --- |
| `runs`, `run_companies` | Пакеты, их состав, состояние компании в пакете и последний сбой |
| `companies` | Название, уникальный RUT, состояние и время поиска |
| `company_documents` | Связь компании с CVE и данные найденного действия |
| `documents` | CVE с учётом регистра, стадия проверки, `codigo`, URL и ошибка |
| `document_files` | Путь относительно каталога БД, SHA-256, размер и время скачивания |
| `attempts` | История попыток, процесс, время, длительность, результат и ошибка |
| `events` | Переходы документа между проверкой, готовой ссылкой, загрузкой и ошибкой |

Примеры состояний: `pending`, `searching`, `downloading`, `downloaded`, `partial`,
`captcha_required`, `proxy_failed`, `missing_pdf`. `partial` означает, что у
компании есть PDF, но ещё не все запрошенные документы скачаны. Раньше компания
могла получить `downloaded`, если скачался хотя бы один PDF; импорт пересчитывает
полноту по найденным CVE. Поэтому число полностью завершённых компаний после
импорта может отличаться от старого отчёта, хотя сами PDF сохраняются.

### Посмотреть существующий сбор без повторного запуска

После обновления кода и пересборки образа зарегистрируйте старые JSON,
манифесты и PDF в общей БД. Команда не обращается к сайтам, не открывает браузеры
и не переписывает исходные файлы. Повторный импорт не дублирует попытки/CVE.
Активный сбор того же пакета блокирует импорт; текущую БД в это время можно читать.

```bash
docker compose --env-file .env.res -f compose.res.yml build res

docker compose --env-file .env.res -f compose.res.yml run --rm res track \
  --run-id res-2025-01-100 --action sync

docker compose --env-file .env.res -f compose.res.yml run --rm res track \
  --run-id res-2025-01-100 --action errors
```

Если старый пакет скачивал только один PDF на компанию, добавьте к `sync`
`--max-documents 1`. Для прежнего `RES_MAX_DOCUMENTS=0` ничего добавлять не нужно.

Просмотр сводки, всех компаний или документов выбранной компании:

```bash
docker compose --env-file .env.res -f compose.res.yml run --rm res track \
  --run-id res-2025-01-100 --action status

docker compose --env-file .env.res -f compose.res.yml run --rm res track \
  --run-id res-2025-01-100 --action companies

docker compose --env-file .env.res -f compose.res.yml run --rm res track \
  --run-id res-2025-01-100 --action documents --company 'RUT_КОМПАНИИ'
```

`--company` также принимает часть названия. В списке компаний есть `cves_found`,
`pdfs_saved`, `missing_cves`, `status` и `error`. В документах — конкретный CVE,
статус, путь, размер, SHA-256, ссылка и ошибка. `errors` показывает незавершённые
и ошибочные компании; нормальные ответы `not_found`/`no_cve_found` видны в общем
списке. Текущая проверка файла по SHA-256 выполняется при импорте и продолжении;
обычный просмотр не сканирует заново все PDF.

### Продолжение и увеличение выборки

Существующие `state.json`, отчёты и манифесты остаются совместимыми. SQLite
сохраняет поиск/CVE, ссылки и документы независимо от JSON; при подготовке
очереди из неё восстанавливаются недостающие рабочие чекпоинты. Исчезнувшие или
повреждённые PDF не считаются скачанными после проверки.

После импорта текущего пакета можно создать следующий, например:

```dotenv
RES_LIMIT=1000
RES_RUN_ID=res-2025-01-1000
```

При последовательном запуске нового пакета ранее найденные компании и готовые
PDF используются из общей БД. На одном файловом разделе PDF подставляются
через hard link; если он недоступен — локально копируются. Повторных сетевых
скачиваний нет, и восстановленные файлы не повышают `new_pdfs` или PDF/мин.
Частично обработанные компании докачивают недостающие CVE. Не удаляйте общую
БД и каталог данных между пакетами. Это учёт для процессов на одном сервере,
а не распределённая очередь нескольких серверов.

Для измерения скорости полностью нового сбора нужен отдельный каталог данных
(`RES_DATA_DIR`) или отдельные `--output`/`--tracking-db`: одного нового run-id
теперь недостаточно, поскольку общая БД переиспользует готовые результаты.

## Остановки по серии ошибок и ответы HTML вместо PDF

`RES_MAX_FAILURES` ограничивает серию неудачных попыток, включая отложенные
повторы. Оставшиеся компании получают `stopped`; среди них могут быть и ещё
не начатые, и отложенные после первой попытки. Это не означает, что каждая из
них уже проверена дважды. Подробности находятся в `attempts` и отчётах процессов.

Новые отчёты процессов содержат `stop_reason` с кодом и порогом ошибки, итоговый
`summary.json` — `worker_stop_reasons`. Частичная очередь возвращает код выхода
`2`, даже если процесс успел сохранить несколько PDF. Telegram перечисляет
причины остановок. Старые отчёты без этого поля автоматически не дополняются.

Неожиданный HTML при GET сертификата получает статус `download_failed`.
Сохранённый `codigo` остаётся в кеше; такой ответ сам по себе не запускает новую
CAPTCHA. Автоматическая повторная проверка устаревшей ссылки сохраняется для
HTTP 302. Для остальных сбоев нужен анализ ответа, а не предположение о сроке
действия кода.

При следующем таком сбое процесс сохраняет в `workers/wXX/diagnostics/`:

- JSON: CVE, HTTP-статус, тип содержимого, заголовок страницы, путь редиректа,
  размер и SHA-256 ответа;
- приватный `.body` — первые 64 КиБ ответа. Он может содержать данные сессии;
  не публикуйте его целиком.

Путь к диагностике присутствует в результате документа и ошибке SQLite.
Подробности аудиосбоя сохраняются также на уровне конкретного CVE в `stages`
и `audio_events`; общий текст `No stage accepted...` не заменяет эти причины.
Явный отказ Google в аудио происходит до распознавания и не устраняется
увеличением числа попыток Whisper. Счётчики повторяющихся сообщений в JSON
могут включать один и тот же сбой на нескольких уровнях — их нельзя суммировать
как количество уникальных неудачных запросов.

## Общая пауза после серии ошибок

По умолчанию вместо первой остановки по `RES_MAX_FAILURES` весь текущий пакет
делает паузу на 10 минут:

```dotenv
RES_MAX_FAILURES=20
RES_ERROR_COOLDOWN_MINUTES=10
RES_MAX_COOLDOWNS=3
```

Порог считается по серии неудачных попыток компаний одного процесса. Когда
любой процесс достигает его, остальные присоединяются к общей паузе. Уже
начатая проверка/загрузка документа завершается; перед следующей компанией
или CVE проверяется пауза. Браузеры и HTTP-сессии закрываются перед ожиданием.
Во время ожидания новые прокси-сессии и задачи не запускаются.

Все процессы используют один срок в таблице `run_controls`: одновременные
отказы пяти процессов не продлевают его до 50 минут. После ожидания счётчик
серии ошибок сбрасывается, очередь продолжается с сохранённых CVE и PDF.
Пауза не расходует дополнительную попытку отложенной компании. Ограничения
попыток на компанию и бюджета прокси остаются в силе.

Telegram присылает отдельные сообщения «пауза до … UTC» и «сбор продолжается»
независимо от интервала периодических уведомлений. События `paused`, `resumed`
и `exhausted` сохраняются в `events` со стадией `cooldown`. Периодический
прогресс показывает активную паузу. Время ожидания включается в общее время
запуска и в расчёт PDF/мин.

После трёх общих пауз следующая серия ошибок останавливает остаток пакета с
причиной `cooldown_limit_reached`. Это конечный бюджет на запуск, а не три
паузы для каждого из пяти процессов. Новый явный запуск после остановки
получает новый бюджет. Если контейнер остановлен в середине активной паузы,
при продолжении сохраняются её срок и уже использованное число пауз.
Ошибка, классифицированная как отказ авторизации прокси, останавливает процесс
сразу; ожидание не исправляет реквизиты доступа.

`RES_ERROR_COOLDOWN_MINUTES=0` или `RES_MAX_COOLDOWNS=0` возвращает прежнюю
остановку без паузы. Менять эти настройки можно с тем же `RES_RUN_ID`; размер,
год/месяц и раскладку браузеров выборки менять при этом не нужно.
Обновление схемы SQLite выполняется автоматически без удаления данных.
